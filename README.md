# MiniBoard

게시글 작성, 조회, 수정, 삭제를 지원하는 Spring Boot 기반 미니 게시판 프로젝트입니다.

## 프로젝트 개요

- 진행 기간: 2일
- 프로젝트 형태: 개인 프로젝트
- 목표:
  - Spring Boot와 JPA를 활용해 게시판 CRUD의 전체 흐름을 직접 구현하는 것
  - 단일 페이지 기반 프론트엔드와 REST API를 연결해 게시글 관리 기능을 완성하는 것
  - 요청/응답 로깅과 입력값 검증을 적용해 기본적인 백엔드 운영 관점까지 경험하는 것

## 서비스 소개

MiniBoard는 게시글을 작성하고, 목록을 조회하고, 상세 내용을 확인하고, 수정 및 삭제할 수 있는 간단한 게시판 서비스입니다.

백엔드는 `/posts` 경로를 중심으로 게시글 생성, 단건 조회, 목록 조회, 수정, 삭제 기능을 제공하며, 프론트엔드는 HTML, CSS, JavaScript로 구성된 단일 페이지에서 검색, 페이지 이동, 상세 조회, 작성/수정 폼 전환까지 처리할 수 있도록 구현했습니다. 게시글은 제목, 내용, 작성자, 생성일시, 수정일시 정보를 포함하며, 목록 조회는 `Pageable` 기반 페이지네이션으로 동작합니다.

## 맡은 역할

- 게시판 CRUD API 설계 및 구현
- 게시글 엔티티 및 JPA 저장 구조 설계
- 요청/응답 DTO 설계
- 단일 페이지 프론트엔드 화면 구현
- 요청/응답 로깅 필터 구현
- 유효성 검증 적용

## 담당 기능 상세

### 1. 게시글 CRUD API 구현

- 게시글 작성 API 구현
- 게시글 단건 조회 API 구현
- 게시글 목록 조회 API 구현
- 게시글 수정 API 구현
- 게시글 삭제 API 구현
- 컨트롤러에서 `PostService`를 호출하는 구조로 API 책임을 분리함

### 2. 게시글 도메인 설계

- 게시글 엔티티에 제목, 내용, 작성자, 생성일시, 수정일시를 포함하도록 설계
- `@PrePersist`, `@PreUpdate`를 통해 생성 시각과 수정 시각이 자동 반영되도록 구성
- 수정 시에는 `update()` 메서드를 통해 제목과 내용만 변경되도록 제한함

### 3. DTO 및 입력값 검증 적용

- 게시글 생성 요청 DTO와 수정 요청 DTO를 분리
- 제목 최대 길이, 작성자 최대 길이, 공백 불가 조건을 검증
- 응답 DTO를 별도로 두어 엔티티를 직접 노출하지 않도록 구성함

### 4. 페이지네이션 기반 목록 조회

- 게시글 목록 조회에 `Pageable`과 `Page<PostResponse>`를 적용
- 프론트엔드에서는 페이지 번호와 size를 조절하며 목록을 조회하도록 구현
- 백엔드가 Page 응답을 줄 경우 이를 그대로 사용하고, List 응답일 경우 프론트에서 보정할 수 있도록 구성함

### 5. 단일 페이지 프론트엔드 구현

- 게시글 검색 입력창, 페이지 이동 버튼, size 선택 기능 구현
- 게시글 목록 클릭 시 상세 조회 기능 구현
- 새 글 작성과 수정이 같은 폼을 공유하도록 구성
- 삭제 확인, 토스트 메시지, 상태 전환 로직을 적용해 사용성을 높임

### 6. 요청/응답 로깅 기능 구현

- `OncePerRequestFilter` 기반의 요청/응답 로깅 필터 구현
- 요청 URI, 상태 코드, 처리 시간, JSON 바디를 함께 기록하도록 구성
- 비밀번호, 토큰 등의 민감 정보는 마스킹 처리
- 정적 리소스, actuator, swagger 경로는 로그 대상에서 제외하여 노이즈를 줄임

## 기술적 의사결정

### 왜 엔티티와 DTO를 분리했는가

게시글 생성, 수정, 응답에 필요한 데이터 형태가 서로 다르기 때문에 요청 DTO와 응답 DTO를 분리했습니다. 이를 통해 엔티티를 직접 외부에 노출하지 않고, API 목적에 맞는 데이터 구조를 명확히 유지할 수 있도록 했습니다.

### 왜 생성일시와 수정일시를 엔티티 내부에서 관리했는가

게시글 생성과 수정 시점을 일관되게 관리하기 위해 `@PrePersist`, `@PreUpdate`를 사용했습니다. 이 방식은 서비스 계층에서 매번 시간을 직접 넣지 않아도 되어 중복을 줄이고, 엔티티 생명주기에 맞는 자동 갱신이 가능하다는 장점이 있습니다.

### 왜 요청/응답 로깅 필터를 별도로 두었는가

게시글 기능을 개발하면서 API 흐름을 빠르게 추적하고 디버깅하기 위해 요청/응답 로깅 필터를 분리했습니다. 특히 JSON 바디를 확인할 수 있도록 캐싱 래퍼를 사용하고, 민감정보는 마스킹하도록 하여 단순 로그 출력보다 실제 운영 관점에 가까운 구조를 고민했습니다.

### 왜 프론트엔드를 단일 페이지로 구성했는가

백엔드 API를 직접 테스트하고 게시글 흐름을 한 화면에서 확인하기 위해 단일 페이지 형태로 구성했습니다. 목록 조회, 상세 조회, 작성, 수정, 삭제를 모두 한 화면에서 처리할 수 있어 API 동작을 빠르게 검증하기에 적합했습니다.

## 문제 해결 경험

### 문제

게시글 API는 구현했지만, 실제로 기능이 제대로 동작하는지 반복적으로 확인하려면 별도의 테스트용 UI가 필요했습니다.

### 해결

목록, 상세, 작성, 수정, 삭제를 모두 처리할 수 있는 단일 페이지를 만들고, 검색 입력, 페이지 이동, 토스트 메시지, 폼 모드 전환 기능을 추가했습니다. 이를 통해 Postman만 사용하는 방식보다 훨씬 빠르게 게시글 흐름을 검증할 수 있었습니다.

### 결과

게시글 생성 후 목록 반영, 상세 조회, 수정 후 재조회, 삭제 후 목록 갱신까지 전체 흐름을 한 화면에서 반복 확인할 수 있게 되었고, 백엔드와 프론트엔드 연동 경험까지 함께 쌓을 수 있었습니다.

## 트러블슈팅

### 1. 요청과 응답 로그를 남길 때 바디가 사라지는 문제

#### 문제

서블릿 환경에서 요청과 응답 바디를 바로 읽으면 이후 처리 과정에서 바디가 소진되어 정상 응답에 영향을 줄 수 있습니다.

#### 원인

HTTP body는 한 번 읽고 나면 다시 사용할 수 없는 구조이기 때문에, 단순히 filter에서 읽어버리면 컨트롤러나 응답 처리에 문제가 생길 수 있습니다.

#### 해결

`ContentCachingRequestWrapper`와 `ContentCachingResponseWrapper`를 사용해 요청과 응답을 감싼 뒤, 필터 체인이 끝난 뒤 캐시된 바디를 읽도록 구현했습니다. 응답은 마지막에 `copyBodyToResponse()`를 호출해 실제 클라이언트로 정상 전달되도록 했습니다.

#### 배운 점

로깅은 단순 출력이 아니라 HTTP 처리 흐름을 깨지 않도록 설계해야 하며, 운영용 로그는 안전성과 디버깅 편의성을 함께 고려해야 한다는 점을 배웠습니다.

### 2. 민감한 값이 로그에 그대로 남을 수 있는 문제

#### 문제

요청/응답을 통째로 로그에 남기면 비밀번호나 토큰 같은 민감 정보가 그대로 출력될 수 있습니다.

#### 원인

JSON body 전체를 기록하는 방식은 디버깅에는 편하지만, 보안 측면에서는 위험할 수 있기 때문입니다.

#### 해결

정규식을 활용해 `password`, `accessToken`, `refreshToken`, `token` 필드를 마스킹하는 로직을 추가했습니다. 또한 actuator, swagger, 정적 리소스 경로는 필터 대상에서 제외해 불필요한 로그를 줄였습니다.

#### 배운 점

로그는 많이 남기는 것보다 필요한 정보를 안전하게 남기는 것이 중요하며, 보안과 운영 편의성의 균형을 고려해야 한다는 점을 배웠습니다.

### 3. 생성과 수정에서 입력 조건이 다른 문제

#### 문제

게시글 생성 시에는 작성자가 반드시 필요하지만, 수정 시에는 작성자 변경이 필요하지 않았습니다. 같은 요청 구조를 쓰면 불필요한 입력까지 강제하게 되는 문제가 생길 수 있었습니다.

#### 원인

생성과 수정은 비슷해 보여도 요구 데이터와 허용 범위가 서로 다르기 때문입니다.

#### 해결

`PostCreateRequest`와 `PostUpdateRequest`를 분리해 생성 시에는 제목, 내용, 작성자를 모두 받고, 수정 시에는 제목과 내용만 받도록 설계했습니다. 프론트엔드에서도 작성 모드와 수정 모드를 구분해 작성자 입력 필드의 활성화 여부를 다르게 처리했습니다.

#### 배운 점

비슷한 API라도 목적이 다르면 요청 모델을 분리하는 것이 더 명확하고 유지보수하기 쉽다는 점을 배웠습니다.

## 회고

- 잘한 점
  - 짧은 기간 안에 게시판 CRUD의 전체 흐름을 완성했고, 백엔드 API와 프론트 화면을 함께 연결해 실제 동작까지 확인한 점이 좋았습니다.
  - 요청/응답 로깅과 입력값 검증까지 적용해 단순 CRUD를 넘어서 운영과 안정성 관점도 일부 반영했습니다.

- 아쉬운 점
  - 테스트 코드를 작성하지 않아 기능 검증이 수동 확인에 의존했습니다.
  - 예외 처리 구조가 별도로 보이지 않아 `IllegalArgumentException` 중심의 단순 처리에 머물러 있습니다.
